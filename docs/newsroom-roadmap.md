# خارطة طريق غرفة أخبار النقطة

## المرحلة الحالية
- تثبيت مخطط المحتوى التحريري داخل TinaCMS.
- تجهيز أنواع المواد والحالات التحريرية وحقول المصادر والوثائق والمنهجية وحق الرد.
- توليد فهرس المحتوى من `content/posts` إلى `data/posts.json` و`public/data/posts.json`.
- توفير صفحة `newsroom.html` لعرض المواد المنشورة وقارئ المادة.
- توفير `admin/dashboard.html` كواجهة متابعة تحريرية للمسودات والمراجعة والجاهز للنشر والمنشور.

## المرحلة التالية
1. ربط الواجهة الرئيسية بمصدر محتوى ديناميكي بدل الاعتماد على البطاقات الثابتة.
2. تحسين توليد وفحص فهرس المحتوى آليًا ضمن GitHub Actions.
3. توسيع صفحة المادة الصحفية لتدعم الصور والوثائق والمنهجية وحق الرد والمصادر بصورة تحريرية كاملة.
4. تحويل لوحة غرفة الأخبار من واجهة متابعة إلى نظام تحريري فعلي بعد إضافة المصادقة.
5. تنفيذ المصادقة الحقيقية والصلاحيات Owner / Editor / Writer مع خدمة خلفية وقاعدة بيانات وسياسات وصول على الخادم.
6. إضافة سجل تدقيق للتغييرات: من عدّل المادة، ومتى، وما الذي تغير، ومن وافق على النشر.
7. بعد تثبيت الصلاحيات، تصميم استقبال آمن للمعلومات والوثائق الحساسة مع تشفير وتخزين مضبوط وسياسة احتفاظ واضحة.

## مبدأ مهم
حقل `status` داخل المادة لا يُعتبر نظام صلاحيات أو مصادقة. الصلاحيات الحقيقية يجب أن تُفرض على الخادم/مزود الهوية، وليس عبر واجهة المتصفح فقط.

## أمن المصادر
لا تُستخدم عبارات مثل "حماية المصادر مفعلة" أو "إرسال تسريب آمن" كحقيقة تقنية قبل تنفيذ نظام فعلي للتشفير، التخزين، التحكم بالوصول، وسياسة احتفاظ آمنة.

حتى اكتمال ذلك، يجب أن تكون واجهة الإرسال العامة واضحة للمستخدم بأنها ليست قناة آمنة مخصصة للمصادر الحساسة، وألا تعرض رسالة نجاح توحي بأن البيانات شُفّرت أو حُفظت بأمان إذا لم يحدث ذلك فعليًا.

## معيار التنفيذ قبل الإعلان
أي ميزة أمنية أو تحريرية جديدة تُعتبر مكتملة فقط بعد تحققها في الكود واختبارات التحقق ونجاح مسار النشر. لا تُعرض الواجهة على أنها مصادقة حقيقية أو قناة آمنة قبل ربطها بخدمة خلفية وهوية وقواعد وصول قابلة للتحقق.
